# Recheck 一份使用者編輯後的 proofread 稿

使用者手動編輯了 `_proofread/<檔名>.md`(消化 `<sup>？</sup>`、填 `[？]`、改字),
進入 `/polish` 或結案前,Claude 對使用者改過的版本做一次 cross-check pass,
標出可疑處,**讓使用者決定要不要再改;不要直接改檔案**。

## 輸入

- **必填**:`_proofread/<檔名>.md`(使用者已手改的版本)
- **比對來源**:`_transcripts_clean/<檔名>_{funasr,apple,sensevoice}.txt`(三主力,
  2026-07-05 收斂後「三引擎」指這三個)+ `_firered.txt`(第三票,若存在)、
  以及 `_transcripts_clean/<檔名>_getnote.txt`(若存在)。
  `_faster.txt`(Qwen3 sidecar)只在疑問處涉及**中英混講/英文專名**時查(sidecar,其他位置不算票;數字/日期看 Apple/SenseVoice)
- **參考**:`dictionary.yaml`(專有名詞最終真理)

若 `$ARGUMENTS` 為空:
- **同一個 session 已經在處理某個檔案**(剛跑完 proofread、或使用者剛改完它)
  → 直接用它,說一聲「recheck 的是 XXX」即可,不用停下來等確認
- **冷啟動、或 `_proofread/` 裡有多個近期改動的候選** → 抓最近修改的 `.md`,
  先問「要 recheck 的是 XXX,對嗎?」等確認

若 `$ARGUMENTS` 是檔名,直接開 `_proofread/<檔名>.md`。

## 流程

### 0. 用 git diff 定位使用者改動(優先)

```bash
git diff -- _proofread/<檔名>.md
```

- **有 diff** → diff 到的位置就是使用者實際改動處,cross-check 火力優先集中在這些位置
  (整篇還是要快速通讀一遍,抓 Claude 自己當初校對的漏,但 diff 處逐一比對)
- **沒 diff**(該檔沒 commit 過 Claude 版,或使用者改完已 commit)→ 退回全文通讀模式
- 前提:proofread 產完稿要先 commit 一版,使用者的手改才 diff 得出來
  (proofread.md 結尾有對應提示;跨 session recheck 時這一步尤其關鍵,
  因為 context 裡沒有 Claude 原版可以比)

### 1. 讀 proofread 稿

通讀一遍,標出**自己讀起來覺得有疑問**的位置(字面不通、語意翻轉、搭配怪、
人名長度可疑、可能漏掉的 callback)。

### 2. 對每個疑問處對照三引擎原稿

- 用 grep 或 Read 找 raw / clean 稿對應段落
- 看三引擎原本辨識成什麼
- 判斷使用者的版本可能是:typo / 語意翻轉 / 漏音節 / 漏 callback / 都沒問題

### 3. 列 flag list 給使用者

格式:

```
**L<行號>**「使用者寫的句子」
- 三引擎:funasr 寫「X」、apple 寫「Y」、sensevoice 寫「Z」(firered:「W」,如有)
- 我的看法:[一句話判斷,可能是 typo / 語意翻轉 / 漏字 / callback]
- 建議:[改字建議 / 重聽 / 維持原樣由你判斷]
```

**行號 = 編輯器裡看到的檔案行號**(proofread 稿一段一行,行號就是那一段所在的行),
用 `grep -n '<句子片段>' _proofread/<檔名>.md` 取,不要報「段落 N」— 使用者在編輯器裡
是用跳行找位置的。對話裡和檔尾那份都要標 L<行號>;flag list 附在檔尾不會動到正文行號,
所以兩邊的號碼一致。

範例(取自 2026-04-25-1624 那次):

> **L33**「可是之前我卻沒有反過來想」
> - 三引擎一致是「卻反過來想」(沒有「沒有」)
> - 加了「沒有」會讓語意翻轉:下文「為什麼我不能成為那個小孩」就是反過來想的內容
> - 建議:刪「沒有」

### 3.5 同一份 flag list 固定附寫到檔案底部(必做)

對話裡列完之後,把**同一份 flag list**用 Edit 附加到 `_proofread/<檔名>.md` 檔尾
(使用者在編輯器裡對著改,不用在終端機和編輯器之間來回對照)。固定格式:

```
---

*【recheck flag】處理完請把這一段整段刪掉,不要讓它進 polish 或知識庫*

*1. L<行號>「使用者寫的句子」— 引擎聽到什麼 + 一句話判斷。建議:…*

*2. L<行號>…*
```

- 全段斜體 + 開頭警語,視覺上跟正文區隔
- 標點一律全形(引擎名 funasr/apple 等 ASCII 字母無妨),不要引入半形逗號問號括號
- 這段是**暫時工作區**,不是正文:使用者處理完自己整段刪掉
- **沒有任何 flag 時不要附加**(不要把「沒問題」寫進檔案)
- 附加只動檔尾,不碰正文(使用者可能同時在編輯器裡改檔,Edit 的 old_string 抓檔尾錨點)

### 4. 結尾

列完之後等使用者決定。**不要**主動進 `/polish`,也**不要**自己改檔案的正文
(檔尾附加 flag list 是唯一例外)。
使用者讀完 flag list,接受幾個就改幾個,然後她會自己呼叫 `/polish` 或結案。
`/polish` 或結案時若發現 recheck flag 段還留在檔案裡,提醒使用者刪掉,不要帶進下游。

## 要 flag 的(三類 + 兩個特例)

### 三類主軸

1. **明顯字面不通**:語法或詞彙搭配明顯怪
   - 例:「我哥很也有去嘛」(「很也」搭配讀不通)
   - 例:「不太不愛、不太愛」(兩個「不太」連用語意打架)

2. **語意翻轉**:漏字 / 多字導致意思跟下文相反
   - 例:「失去敢和別人互動」跟下文「不怕摔倒」(正向描述)不協調
   - 例:加了一個「不」或「沒有」讓整段邏輯反轉

3. **dict.yaml 沒對齊**:專有名詞跟詞典寫法不一致
   - 例:稿子寫「特麗莎」,dict.yaml 寫「特蕾莎」

### 兩個特例(來自過去踩過的雷)

4. **三引擎一致仍漏音節**:dict 沒收的短人名,警覺中間是否吞了輕音節
   - 例:三引擎都寫「丹娜」(2 字),實際是「戴安娜」(3 字),漏中間「安」
   - 對「短促 2 字人名」+ dict 沒收的位置,提示使用者確認音節長度
   - 警覺輕聲節「安 / 恩 / 娜 / 拉 / 利」常被吞

5. **漏掉的 callback**:前段提到的影集 / 書 / 概念,後段音節相近但被當辨識誤
   - 例:前段「捫心問診」(HBO 影集),後段「人們新問」/「冷門性問」/「先問」
     這種三引擎全錯但音節 stem 一致(問/診/心)的位置 → 可能是 callback,
     不是辨識誤差
   - 觸發條件:三引擎全錯但音節 stem 接近 + 該位置語境呼應前段引用 → 主動回頭找
     callback,不要當隨機辨識誤打發掉

## 不要 flag 的

- **口語的繞、重複、停頓**(那是素材的一部分)
- **「就是」「然後」「我覺得」「嗯」「欸」**(語氣 / 思緒節奏)
- **`[註:...]`**(使用者的 meta-note,Claude 永遠不碰)
- **`<sup>字？</sup>` 標記本身**(使用者沒消化就是還沒消化,不用提醒她,
  除非那個位置三引擎其實有共識可以拿掉)
- **使用者明顯刻意保留的繞口句**(比照 proofread 規則,不潤稿)
- **半形 vs 全形標點**(那是格式問題,不是 typo)

## 操作哲學

- **使用者有耳朵記得**:她改的位置可能是基於聽過音檔的判讀,Claude 的 flag 是
  「以防萬一漏掉」,不是覆蓋判斷
- **寧可不 flag,不要過度 flag**:flag list 太長使用者會疲乏,只挑真正可疑的
- **三引擎沒共識也不一定是 typo**:口語本來就模糊,如果使用者的版本讀得通就
  別動

## 結尾回報

回報格式:

> 找到 N 處可能要回看,列在上面,同一份也附在檔案底部(處理完記得把那段整段刪掉)。
> 沒有的話就是讀起來都通,可以接著 `/polish`。

不要自誇「我幫你抓到 X 個錯」,也不要建議使用者全部接受。讓她自己決定。
