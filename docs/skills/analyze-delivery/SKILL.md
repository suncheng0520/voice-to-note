# Analyze Delivery

用於 `voice-to-note` 專案的口條/錄音表達追蹤。使用者說「分析口條」時，預設幫他重跑指標、保存報告，並補上少量人工觀察。

## 預設工作流

1. 確認目前在 `voice-to-note` 專案根目錄，且存在：
   - `scripts/analyze_delivery.py`
   - `docs/口條基準-2026-06-30.md`
   - `_transcripts_raw/`
2. 先讀 `docs/口條基準-2026-06-30.md`，把 2026-06-30 當基準。
3. 判斷分析區間：
   - 使用者指定日期或月份時，照指定區間跑。
   - 沒指定時，找 `docs/口條指標-*.md` 最新一份；若沒有，從 `2026-07-01` 跑到今天。
   - 輸出檔名用 `docs/口條指標-YYYY-MM.md`；若是非整月區間，用 `docs/口條指標-YYYY-MM-DD.md`。
4. 執行：

   ```bash
   python3 scripts/analyze_delivery.py --since YYYY-MM-DD --until YYYY-MM-DD --output docs/口條指標-YYYY-MM.md
   ```

   若使用者要全量重跑，執行：

   ```bash
   python3 scripts/analyze_delivery.py --output docs/口條指標-YYYY-MM-DD.md
   ```

5. 人工抽看最近 2-3 份相關逐字稿或 `_proofread` 檔，觀察：
   - 開頭是否有主問題或今日三題。
   - 轉場是否有路標句。
   - 收尾是否有「我今天其實想說的是什麼」。
   - 是否有當下 3 分鐘補錄的痕跡。
6. 回覆使用者時用繁體中文，保持短而有判斷：
   - 報告存在哪裡。
   - 這次區間的核心數字。
   - 和 2026-06-30 基準相比的趨勢。
   - 1-3 個最值得保留/改進的口條觀察。
   - 下一輪最小練習。

## 解讀口徑

- `就是 / 其實 / 然後 / 我覺得` 是思考踏板，不是錯字。不要把下降當唯一目標；重點是功能有沒有變清楚。
- `嗯 / 呃` 更接近發聲停頓或 ASR 捕捉，不要過度解讀。
- 長錄音保留為「自我田野筆記」；3 分鐘補錄才是「收束練習」。
- 若數字下降但人工觀察變得僵硬，要提醒使用者不要把自己講成稿子。
- 若數字上升但有清楚路標與收尾，不一定是退步。

## 常用比較基準

2026-06-30 基準量化範圍：

- 84 份 `_transcripts_raw/*_faster.txt`
- 750,296 字元
- `就是`：11.65 / 千字元
- `其實`：5.65 / 千字元
- `然後`：4.01 / 千字元
- `我覺得`：3.13 / 千字元
- `嗯`：1.47 / 千字元
- `呃`：0.38 / 千字元

## 注意事項

- 不要修改 `_transcripts_raw/`、`_proofread/`、`_polished/` 內容，除非使用者明確要求。
- 若沒有新錄音，告知沒有可分析的新區間，並可全量重跑一次作為檢查。
- 如果腳本失敗，先讀錯誤訊息並修正 `scripts/analyze_delivery.py`，再重跑。
